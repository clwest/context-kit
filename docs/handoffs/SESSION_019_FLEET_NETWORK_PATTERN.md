# Session 019 — fleet-network sub-pattern bundled

## Why this handoff exists

The `infra/fleet-net` networking convention powering
`/Users/donkeyking/development/infra/` (the local anchor that
connects unified-donkey-betz + character-os + their data
services) was distilled into a reusable sub-pattern during
u-d-b session 1117 (2026-05-21), landed there as a working
example at
`unified-donkey-betz/docs/docs-pattern/fleet-network/`. The
README explicitly noted it should be ported into context-kit
as a sub-pattern — same shape as the spokesperson-corpus port
that SESSION_018 shipped.

This session lifts the pattern up into the context-kit bundle
so every project generated by `context-kit init` (or refreshed
via `init --force`) gets it at
`docs/docs-pattern/fleet-network/` automatically. The
proposed CLI subcommand (`context-kit fleet-net init / attach
/ verify / doctor`) is documented as a proposal and
deliberately not implemented yet, matching the
spokesperson-corpus discipline.

## What shipped

### `cli/_pattern/fleet-network/` — new bundled sub-pattern

Four files, ~439 lines total:

- `README.md` — what the pattern is, when to use, the Docker
  Desktop multi-network host-port caveat, what the pattern is
  *not* (not a service mesh, not production plumbing, not a
  fleet-wide compose file).
- `RECIPE.md` — manual setup steps (the future
  `context-kit fleet-net init` CLI should automate these):
  one-time per laptop (create the network + anchor dir +

### `docs/proposals/fleet-network-subcommand.md` — proposal

Captures the proposed `context-kit fleet-net init / attach /
verify / doctor` CLI surface, modeled on the existing
`translation-init` precedent and the spokesperson-corpus
proposal. Intentionally **not implemented** this session.

Key shape choices documented:

- Four verbs (`init`, `attach`, `verify`, `doctor`) — more
  surface area than spokesperson because the pattern has real
  side effects (`docker network connect`, container restarts)
  not just file generation.
- `attach` auto-recovers from the Docker Desktop
  multi-network host-port bug (detect + `docker restart` +
  re-verify + log in manifest's "Known caveats").
- Open question: should the manifest carry a machine-readable
  YAML sidecar so the CLI can read back its own state instead
  of parsing markdown? Probably yes, but deferred to a second
  worked instance.

## Why bundle the pattern now (vs. wait for the CLI)

Same calculus as SESSION_018's spokesperson-corpus decision:

- The pattern's content (RECIPE, templates, the
  Docker Desktop caveat) is the load-bearing part. The CLI
  would be convenience on top.
- Adopters can use the pattern today via `cp -r` against the
  bundle.
- `init --force` already refreshes the entire `_pattern/`
  bundle, so adopters get future improvements for free.
- The pattern still needs a second worked instance (different
  operator, different OS mix, or different stack) before the
  CLI API surface should be locked.

## AI Notes

The bundling pattern from SESSION_018 (sub-pattern lands in a
sibling project as a worked instance first, then gets lifted
into the context-kit `cli/_pattern/` bundle once distilled)
held up cleanly here. Two data points doesn't make a pattern,
but the shape is starting to look like a deliberate workflow:
generalize → live in a sibling → lift into the bundle →
propose the CLI → wait for a second instance → ship the CLI.

The proposal-without-implementation discipline is also
holding. It's the same trade-off as SESSION_018: ship the
content (where the real value lives) without locking the
API (where premature commitment costs the most). The
fleet-network proposal has more API surface than
spokesperson-corpus (four verbs vs three, with real Docker
side effects) so the cost of locking it early would have
been higher — the deferral is genuinely load-bearing here,
not ceremonial.

One shape difference worth flagging: the fleet-network
pattern operates *across* projects (one anchor directory
serving many apps), while every other context-kit pattern
operates *within* a single project. The proposal addresses
this by defaulting `--root` to `$HOME/development` but it's
worth watching whether the cross-project shape stresses the
rest of the context-kit conventions in ways the in-project
patterns don't (e.g. the inventory anchor is per-project; the
fleet manifest is per-laptop). Probably fine — the manifest
isn't an anchor in the context-kit sense — but worth a
second look once `verify` is implemented and starts reading
state across project boundaries.
